## 1. 느린 첫 화면과 중복 네트워크 요청

### 현상

프로그램을 실행할 때 전체 종목 동기화, 계좌 조회, 환율 조회와 종목별 시세 조회가
모두 끝날 때까지 화면이 비어 있었습니다. 실계좌 기준 첫 화면까지 약 5.81초가 걸렸고,
5초 자동 갱신이 초기 로딩과 겹치면 같은 요청이 중복될 가능성도 있었습니다.

### 원인

- 모든 작업을 하나의 동기 흐름으로 처리했습니다.
- 매 실행마다 변경 빈도가 낮은 전체 종목 마스터까지 동기화했습니다.
- 핵심 계좌 데이터와 부가적인 종목 시세의 우선순위를 구분하지 않았습니다.

### 해결

데이터 로딩을 세 단계로 나눴습니다.

```text
SQLite snapshot ──즉시──> 이전 정상 화면
                            │
계좌·환율 API ────────────> 핵심 데이터 교체
                            │
종목 시세·분석 ───────────> 비동기 보강
```

마지막 정상 대시보드를 SQLite에 저장해 다음 실행에서 먼저 표시하고, 계좌·환율을
핵심 단계로 가져온 다음 종목별 시세와 분석을 보강하도록 변경했습니다. 전체 종목
동기화는 최초 캐시가 없거나 사용자가 `:s`를 실행할 때만 수행하고, 로딩 상태를 추적해
자동 갱신과 중복 실행되지 않게 했습니다.

### 결과

| 단계 | 측정 시간 |
|---|---:|
| SQLite 캐시 화면 준비 | 0.527ms |
| 최신 잔고·보유종목 핵심 조회 | 1.024초 |
| 현재가 14개와 급등 분석 보강 | 3.388초 |

빈 화면 대기 대신 캐시 화면은 1ms 미만에 나타나고, 약 1초 후 최신 핵심 데이터로
교체됩니다. 전체 최신화 시간보다 사용자가 처음 정보를 볼 수 있는 시간을 우선하는
방식으로 체감 성능을 개선했습니다.

## 2. NH 호출 제한과 잔고 API 중복 호출

### 현상

짧은 시간에 `IGW42903` 호출 건수 초과가 발생했습니다. 화면 하나를 갱신하는 과정에서
잔고 합계와 보유 종목을 각각 얻기 위해 동일한 계좌 API를 반복 호출하고 있었습니다.

### 원인

애플리케이션 포트에는 `Balance`와 `Positions`가 분리돼 있지만 NH API는 한 잔고
응답에 두 정보가 함께 들어옵니다. 포트 구조를 그대로 네트워크 요청에 대응시키면서
같은 계좌에 중복 요청이 발생했습니다.

### 해결

NH 어댑터 내부에 계좌별 짧은 수명의 잔고 응답 캐시를 두고, 한 응답을 `Balance`와
`Position` 변환에 함께 사용했습니다. HTTP 401에서만 토큰을 한 번 갱신하고, 429는
인증 실패로 취급하지 않아 토큰 재발급과 추가 요청이 이어지지 않게 했습니다.

### 결과

애플리케이션 포트의 명확한 책임은 유지하면서 증권사별 API 특성은 어댑터 내부에서
최적화했습니다. 호출 제한 오류와 불필요한 토큰 발급을 함께 줄였습니다.

## 3. 재실행마다 반복되는 NH 토큰 발급 알림

### 현상

NH 접근 토큰은 약 24시간 유효하지만 앱을 다시 실행할 때마다 새 토큰을 발급해 사용자에게
보안 알림이 반복해서 전송됐습니다.

### 원인

토큰을 프로세스 메모리에만 보관했기 때문에 프로그램 종료와 함께 유효한 토큰 정보가
사라졌습니다.

### 해결

접근 토큰과 만료 시각을 OS 키링에 저장하고, App Key의 짧은 해시를 함께 기록해 다른
키의 토큰이 재사용되지 않게 했습니다. 만료 1분 전까지 기존 토큰을 사용하고 서버가
401을 반환할 때만 캐시를 삭제한 뒤 한 번 재발급합니다. 로컬 테스트 서버에서는 실제
키링을 사용하지 않도록 토큰 캐시를 비활성화했습니다.

### 결과

프로그램을 재실행해도 유효한 토큰을 재사용하게 되어 토큰 발급 알림과 인증 요청 횟수가
감소했습니다. 토큰은 SQLite나 설정 파일에 평문으로 저장되지 않습니다.

## 4. 새 터미널에서 OS 키링 자격증명을 읽지 못함

### 현상

`minstock setup` 직후에는 정상 연결됐지만 새 터미널에서 `--diagnose`를 실행하면
자격증명이 미설정으로 표시되는 사례가 있었습니다. 키링 backend는 `exit status 36`을
반환했습니다.

### 원인

자격증명이 삭제된 것이 아니라 macOS 로그인 키체인이 잠겨 비대화형 프로세스의 접근이
거부된 상태였습니다. 초기 구현은 `keyring.Set`의 성공만 확인해 실제 저장소에서 다시
읽을 수 있는지는 검증하지 않았습니다.

### 해결

저장 직후 키링 backend에서 App Key와 Secret을 다시 읽어 입력값과 일치하는지 검증하고,
진단 화면에 `environment`와 `os-keyring` 출처를 구분해 표시했습니다. 키체인이 잠긴 경우에는
다음처럼 잠금을 해제한 뒤 다시 진단할 수 있습니다.

```sh
security unlock-keychain "$HOME/Library/Keychains/login.keychain-db"
minstock --diagnose
```

### 결과

저장 API의 반환값과 실제 영속화를 분리해 진단할 수 있게 됐습니다. 편의를 위해 키체인
자동 잠금을 끄는 대신, 필요할 때 명시적으로 잠금을 해제하는 보안 원칙을 유지했습니다.

## 5. 서로 다른 증권사 응답과 통화 체계

### 현상

키움과 NH는 계좌 ID, 종목코드, 미국주식 티커, 거래소, 평가금액과 손익 필드가 서로
달랐습니다. API 응답 구조를 화면에서 직접 사용하면 공급자별 조건문이 TUI 전체로
퍼지고 USD와 KRW 합산 기준도 불명확해졌습니다.

### 원인

외부 API의 전송 모델과 화면이 필요로 하는 도메인 모델을 분리하지 않은 것이 문제였습니다.

### 해결

`Account`, `Balance`, `Position`, `Symbol`, `Quote`, `Candle` 공통 모델과 작은 포트
인터페이스를 정의했습니다. 각 증권사 어댑터가 응답을 공통 모델로 변환하고, 통화는
원통화 값을 보존한 채 기준환율이 있을 때만 KRW로 환산합니다. 금액 계산에는
`shopspring/decimal`을 사용했습니다.

### 결과

TUI와 애플리케이션 서비스에서 증권사별 필드명을 제거했고, 새 공급자를 추가할 때
어댑터 구현에 변경 범위를 한정할 수 있게 됐습니다.

## 6. 한글과 ANSI 색상이 포함된 표 정렬

### 현상

한글 종목명과 손익 색상을 함께 표시하면 열 경계가 어긋났습니다. Go 문자열 길이나
일반 `fmt` 폭 지정은 터미널에서 실제로 차지하는 너비와 달랐습니다.

### 원인

- 한글은 일반적으로 터미널에서 두 칸을 차지합니다.
- ANSI 색상 코드는 문자열 길이에는 포함되지만 화면 폭은 차지하지 않습니다.
- 작은 터미널에서 12개 자산 열을 동시에 보여줄 수 없습니다.

### 해결

Lip Gloss의 표시 폭 계산을 사용해 ANSI 코드를 제외한 실제 셀 폭을 기준으로 자르고
패딩했습니다. 선택 배경과 손익 전경색을 분리해 조합하고, 좁은 화면에서는 고정 열과
이동 가능한 열 구간을 나눠 `[`와 `]`로 탐색하게 했습니다.

### 결과

한글·영문·색상 문자열이 섞여도 표 정렬이 유지되고, 터미널 폭이 작아도 전체 자산
필드를 포기하지 않고 확인할 수 있습니다.

## 7. Vim 단축키와 검색 입력 포커스 충돌

### 현상

화면 이동 숫자키, `j`/`k`, 콜론 명령과 검색어 입력이 같은 키 이벤트를 사용해 검색창에
명령 문자가 들어가거나 입력 중 화면이 전환되는 문제가 있었습니다.

### 원인

키의 의미를 현재 화면과 입력 상태보다 먼저 전역 단축키로 해석했습니다.

### 해결

키 처리 우선순위를 `도움말/명령 팝업 → 검색 입력 → 상세 화면 → 전역 이동` 순서로
구성했습니다. 검색 화면도 일반·입력·선택 상태를 분리하고, `:` 명령은 다음 한 키로
완료되는 작은 상태 머신으로 구현했습니다.

### 결과

같은 키를 사용해도 현재 상태에 따라 의미가 명확해졌고, 키보드 중심 탐색과 자유로운
검색 입력을 함께 지원할 수 있게 됐습니다.

## 8. 데모 데이터가 실사용 DB에 남는 문제

### 현상

API 키 없이 데모 모드로 실행한 뒤 실제 계정을 연결하면 샘플 관심종목이 SQLite에 남아
실제 관심종목과 섞였습니다.

### 원인

데모 공급자가 생성한 샘플 그룹과 사용자가 직접 만든 로컬 관심종목을 같은 생명주기로
관리했습니다.

### 해결

DB 마이그레이션에서 provider-owned 샘플 그룹만 제거하고, 사용자가 `m`으로 만든 로컬
기본 그룹은 보존하도록 정리 규칙을 추가했습니다.

### 결과

데모에서 실제 API 모드로 전환해도 샘플 데이터가 섞이지 않으며, 사용자가 직접 구성한
관심종목은 유지됩니다.

## 9. 실서비스 연결 오류

### 키움 `8050: IP가 등록되지 않았습니다`

**현상:** App Key를 정상적으로 읽었지만 토큰 발급이 거절됐습니다.

**원인:** 키 오류가 아니라 현재 네트워크의 공인 IP가 키움 App Key에 등록되지 않은
상태였습니다. 집·회사·VPN에 따라 공인 IP가 달라질 수 있습니다.

**해결:** 키움 REST API의 계좌 App Key 관리 화면에 현재 공인 IP를 등록하고, 진단에서
자격증명 유무와 서버가 반환한 인증 사유를 구분했습니다.

### 나무PLUG QR 오류 `91800`

**현상:** API 신청 QR을 모바일 앱으로 열었을 때 요청 정보가 없거나 만료됐다는 오류가
발생했습니다.

**원인:** QR은 PC 브라우저가 만든 짧은 수명의 인증 요청이므로 이전 화면의 코드를 다시
사용할 수 없습니다.

**해결:** PC 페이지를 새로고침한 직후 새 QR을 스캔했습니다. 이 단계는 minstock의 OAuth
구현이 아니라 API 키 발급 전 포털 인증 과정임을 분리해 확인했습니다.

### NH가 `mock connected`로 표시됨

**현상:** 설정에서 `mode = "live"`로 바꿨지만 모의 서버에 연결됐습니다.

**원인:** 실제 연결 대상은 mode 문자열이 아니라 `base_url`이며, 주소가
`https://moapi.nhplug.com:8443`로 남아 있었습니다.

**해결:** `mode`, `base_url`, `auth_url`을 함께 검증하고 운영 연결에서는 API와 인증
주소를 모두 운영 도메인으로 설정했습니다.

### 연결됐지만 NH 종목이 보이지 않음

**현상:** 토큰 발급은 성공해 `Connected`로 표시되지만 보유 종목이 비어 있었습니다.

**원인:** 연결 상태는 인증 성공만 뜻하며, 국내 잔고 필수 입력값 누락과 해외주식 잔고
미구현은 별개의 데이터 문제였습니다.

**해결:** 국내 잔고에 정규장 기준 필수값 `aly_qut_cd=1`을 추가하고, 해외주식 잔고
응답의 `Output_1`을 USD 포지션으로 변환해 미국주식 탭에 합쳤습니다.

## 10. 키움 미연결 시 NH 미국자산이 0원으로 표시됨

### 현상

NH는 정상 연결되고 미국주식 탭에도 보유 종목이 보이지만, 키움 연결이 실패한 상태에서
현황 화면은 다음처럼 표시됐습니다.

```text
원화환산  국내자산 금액만 표시
평가손익  0원
미국자산  $0.00
미국손익  $0.00
USD/KRW   -
```

미국주식 탭에서 `c`를 눌렀을 때 원화 금액이 `₩-`로 나오기도 했습니다. 수정 코드를
푸시한 뒤에도 같은 화면이 계속 보여 처음에는 코드 변경이 반영되지 않은 것으로
오인하기 쉬웠습니다.

### 원인

서로 독립적인 세 문제가 겹쳤습니다.

1. NH 해외주식 잔고는 `Positions`에만 추가되고 통합자산이 사용하는 `Balances`에는
   포함되지 않았습니다. 따라서 미국주식 표에는 종목이 보여도 현황 합계에서는
   누락됐습니다.
2. USD/KRW 공급자로 키움만 등록돼 있어 키움 인증이 실패하면 NH가 제공한 원화
   평가금액과 환율을 활용하지 못했습니다. NH 운영 응답은 명세의
   `tdt_sby_bse_xcg_rt`를 생략하면서 `krw_eal_amt`, `krw_eal_pls_amt` 같은 원화
   평가값만 반환하는 경우도 있었습니다.
3. `origin/main`만 갱신하고 이미 설치된 `$HOME/go/bin/minstock`과 실행 중 프로세스를
   교체하지 않았습니다. Unix 계열에서는 실행 파일을 새로 설치해도 이미 실행 중인
   프로세스의 메모리 코드는 바뀌지 않습니다.

추가로 NH 해외잔고 API가 일시적으로 실패하면 새 스냅샷이 국내 잔고만 포함한 채 이전
정상 화면을 덮어써, 정상 금액과 `$0.00`이 자동 새로고침마다 번갈아 나타났습니다.

### 진단

먼저 실제로 실행되는 파일과 로컬 저장소 버전을 비교합니다.

```sh
type -a minstock
ls -l "$(command -v minstock)"
git status --short --branch
git log -1 --oneline --decorate
```

`main...origin/main [behind N]`이 보이거나 바이너리 수정 시각이 커밋보다 오래됐다면
원격 코드와 실제 실행본이 다릅니다. 실행 중 프로세스가 있는지도 확인합니다.

```sh
pgrep -fl minstock
```

화면에서는 NH가 `connected`인데 미국자산만 `$0.00`인지, 미국주식 탭에는 종목이
있는지를 함께 확인합니다. 이 조합이면 인증 문제가 아니라 해외 `Balance` 집계 경로의
문제입니다.

### 해결

- 한 NH 계좌에서 국내 KRW 잔고와 해외 USD 잔고를 각각 공통 `Balance`로 반환하도록
  다중 통화 잔고 포트를 추가했습니다.
- 해외 잔고 요약의 외화 평가금액·예수금·손익과 원화 평가금액·손익을 함께 보존해
  통합자산에 합산했습니다.
- NH 원화 평가금액과 외화 평가금액의 비율로 NH 기준 USD/KRW를 계산하고, 명시적
  환율이 있으면 그 값을 우선 사용했습니다. 키움 잔고에는 키움 환율만 적용합니다.
- 해외잔고 새로고침이 일시 실패하면 마지막 정상 응답을 유지해 화면을 `$0.00`으로
  덮어쓰지 않도록 했습니다.
- 원격 `main` 반영 후 로컬 작업본과 설치 바이너리도 갱신하고 기존 프로세스를
  종료한 뒤 재실행했습니다.

```sh
git pull --ff-only origin main
make install
# 실행 중인 기존 minstock을 Ctrl+C로 종료한 뒤
minstock
```

시작 직후에는 SQLite의 이전 캐시가 잠깐 보일 수 있습니다. 최신 계좌 조회가 완료되면
나무 해외자산, 손익과 USD/KRW로 교체돼야 하며 이후 일시적인 API 실패에도 마지막 정상
값이 유지돼야 합니다.

### 결과

키움이 `8050` IP 등록 오류로 연결되지 않은 실제 환경에서 NH만으로 원화환산 총자산,
원화 평가손익, 미국자산·손익과 NH 기준 USD/KRW가 표시되는 것을 확인했습니다. 여러 번
자동 새로고침해도 미국자산이 다시 `$0.00`으로 떨어지지 않았습니다.

## 11. 성과 기록과 증권사별 자산 계산이 일관되지 않음

### 현상

현재 잔고는 정상 표시되지만 과거와 비교할 기록이 없어 자산 증감과 추이를 볼 수
없었습니다. 단순히 전체 총액 하나를 저장하면 다음 문제가 생겼습니다.

- 같은 날 앱을 여러 번 실행할 때 중복 기록될 수 있음
- 어느 증권사와 통화가 합계에 포함됐는지 확인할 수 없음
- USD를 어떤 증권사 환율로 원화 환산했는지 사라짐
- 키움 미연결 여부가 NH 자산 행과 전체 합계에 영향을 줄 수 있음

### 원인

기존 대시보드는 현재 시점의 `Snapshot`을 빠르게 표시하는 캐시만 있었고, 날짜별 금융
원장을 보존하는 저장 구조가 없었습니다. 또한 통합 합계를 잔고 전체에서 직접 계산하면
증권사별 중간 결과와 환율 선택 과정을 검증하기 어려웠습니다.

### 해결

증권사·해시 계좌 참조·통화를 복합 키로 하는 `portfolio_snapshots`를 추가하고 같은
날짜의 행은 upsert했습니다. 원통화와 원화 환산 현금·매입금액·평가금액·손익, 적용
환율을 함께 저장하되 원계좌번호와 자격증명은 저장하지 않습니다.

조회 시에는 다음 순서로 계산합니다.

1. 날짜별로 모든 증권사·통화 행을 합산한다.
2. 직전 날짜와 총자산을 비교해 증감액과 증감률을 계산한다.
3. 주·월·연 그래프는 각 기간의 마지막 날짜를 대표값으로 사용한다.
4. 증권사별 `Balance`를 먼저 집계한 뒤 그 결과로 전체 합계를 만든다.
5. USD는 잔고의 자체 환율 또는 같은 증권사가 제공한 환율만 사용한다.

성과 화면은 `Tab`으로 표와 선 그래프를 전환하고 그래프에서 `t`로 일·주·월·연 주기를
바꿉니다. 평가손익·자산 증감·증감률과 대시보드 손익은 양수 빨강, 음수 파랑, 0 흰색으로
통일했습니다. 색상 적용 전 `fitCell`로 셀을 맞춰 ANSI 코드가 정렬 폭에 영향을 주지
않게 했습니다.

### 결과

키움이 미연결이어도 NH 행과 전체 합계가 독립적으로 계산되며, 미연결 증권사는
`데이터 없음`으로 표시됩니다. 일별 기록에서 일·주·월·연 총자산 추이를 볼 수 있고,
증권사별 총자산·손익·수익률·미국자산·적용환율·자산비중을 같은 화면에서 검증할 수
있습니다. 입출금은 아직 별도 현금흐름으로 분리하지 않으므로 자산 증감률이 순수
투자수익률과 다를 수 있다는 주석을 함께 표시합니다.

## 12. 캐시 금액이 실시간으로 보이고 상태 문구가 깨짐

### 현상

시작 직후 SQLite에서 복원한 금액과 NH API 장애 시 마지막 정상 잔고가 화면에 유지됐지만,
사용자는 이 값이 실시간 응답인지 캐시인지 알 수 없었습니다. 긴 상태 문구를 금액 옆과
증권사별 표에 그대로 추가했을 때는 80열 터미널에서 배지와 헤더가 다음 줄로 넘어갔습니다.

### 원인

스냅샷 최상위에는 `Cached` 상태가 있었지만 개별 `Balance`와 `Position`에는 데이터
신선도와 기준 시각이 없었습니다. NH 어댑터는 호출 제한을 피하기 위한 5초 공유 캐시와
일시 장애 시 fallback을 정상 응답과 같은 타입으로 반환했기 때문에 TUI에서 출처를
복원할 수 없었습니다. 또한 한글 상태 문자열은 표시 폭이 2칸이라 바이트 길이나 일반
`fmt` 폭만으로는 80열 배치를 보장할 수 없었습니다.

### 해결

- `Balance`와 `Position`에 `Freshness`와 `AsOf`를 추가했습니다.
- 정상 API 응답은 `LIVE`, NH 공유·장애 fallback은 `CACHED`로 전달합니다.
- SQLite 대시보드 복원은 포함된 모든 증권사 행을 `CACHED`로 표시합니다.
- 한 집계에 live와 cached가 섞이면 `MIXED`로 표시하고, 기준 시각은 가장 오래된 데이터
  시각을 사용합니다.
- USD/KRW 옆에 `[NH·실시간]`, `[키움·캐시]` 형식으로 공급자와 상태를 표시합니다.
- 80열에서는 `●실시간`, `◐혼합`, `○캐시`로 축약하고 넓은 화면에서만 상세 상태와
  `HH:MM:SS` 기준 시각을 표시합니다.

### 결과

금액을 보존하는 장애 대응과 데이터 최신성 표시가 분리됐습니다. NH 해외잔고 새로고침이
실패해 마지막 정상값을 유지할 때도 `캐시`로 보이며, 국내·해외 데이터 상태가 다르면
`혼합`으로 표시됩니다. 환율 제공 증권사도 금액 옆에서 바로 확인할 수 있습니다.
80열과 넓은 화면을 각각 렌더링해 상태 추가 후에도 패널과 표가 줄바꿈되지 않는 것을
확인했습니다.

## 13. 배당 API 호출 제한과 예상 배당의 불확실성

### 현상

증권사 잔고에는 보유수량은 있지만 미국주식·ETF의 배당 이력과 미래 지급 일정이 없어
예상 배당을 계산할 수 없었습니다. 외부 배당 API를 화면 새로고침마다 호출하면 무료
사용량을 빠르게 소진하고, 무배당 종목은 빈 응답 때문에 계속 재호출될 수 있습니다.

### 원인

Alpha Vantage 무료 키는 공식 안내 기준 하루 25회 요청 제한이 있으며 `DIVIDENDS`는
심볼별 endpoint입니다. 또한 미래 데이터는 발행사가 이미 선언한 배당만 확정적으로
존재하므로 향후 12개월 전체 지급액과 지급월을 그대로 제공할 수 없습니다.

최초 구현에서는 배당 화면을 연 채 계좌 자동 갱신이 실행될 때 캐시가 없는 종목을 다시
조회했습니다. 화면 진입 요청과 자동 갱신 요청이 겹치면 같은 심볼도 동시에 호출됐고,
실패 응답은 캐시하지 않아 다음 5초 갱신에서 다시 호출했습니다. 실계좌 재현에서는
`AAPL`, `GOOGL`, `QLD`, `VOO`는 조회됐지만 마지막 `QQQM`에서 일일 한도 초과가
확인됐습니다. API 키와 JSON 변환 문제가 아니라 중복·실패 재시도 정책이 원인이었습니다.

### 해결

- 미국 ETF와 과거·선언된 미래 배당을 지원하는 Alpha Vantage `DIVIDENDS`를 선택했습니다.
- API 키는 `minstock setup dividend`로 OS 키링에 저장하고 환경변수
  `ALPHAVANTAGE_API_KEY`도 지원합니다.
- 심볼별 응답을 24시간 SQLite 캐시하며 빈 응답도 유효한 캐시로 저장합니다.
- 프로그램 재실행 시 마지막 보유종목의 SQLite 캐시만 먼저 읽어 화면을 준비합니다. 이
  시작 경로는 API를 호출하지 않으며, 24시간 이내 캐시는 일반 조회에서도 그대로 재사용합니다.
- 연간 예상치는 최근 12개월 주당 배당 합계 × 현재 보유수량으로 계산합니다.
- 세후 예상치는 미국 원천징수 15%를 가정하며, 원화는 포지션별 증권사 환율로 환산합니다.
- 월별 캘린더는 선언된 미래 지급을 우선하고 나머지는 최근 지급일의 1년 뒤를 예상
  지급월로 사용합니다.
- 배당 화면을 보고 있는 동안 계좌가 5초마다 갱신되더라도 보유종목·수량·환율이 같으면
  배당 보고서를 다시 요청하지 않습니다.
- 같은 종목의 동시 요청은 하나로 합치며, 일반 실패는 15분, 일일 호출 한도 오류는
  24시간 캐시해 반복 호출로 한도 문제가 악화되지 않게 합니다.
- `minstock --diagnose`에서 배당 키가 `미설정`이면 일회성 `export`가 아니라
  `minstock setup dividend`를 실행해 OS 키링에 영구 저장해야 합니다.

### 결과

화면 자동 갱신이 외부 API 호출 증가로 이어지지 않으며, 같은 종목을 여러 증권사에
보유해도 USD 수량은 합산하고 원화는 각 증권사 환율로 계산합니다. 화면에는 데이터
공급자와 캐시 상태를 표시하고, 세후 세율과 미래 지급월이 추정치임을 명시했습니다.
실제 세금과 배당 삭감·증액·중단은 예측할 수 없으므로 세무 또는 투자 판단 자료가 아닌
조회용 예상치로 제한합니다.

실계좌 종단 간 확인에서 API 키의 OS 키링 인식, NH 보유수량 결합, 종목별 배당 조회,
세후 금액과 NH 환율 기반 원화 환산이 정상 동작했습니다. 이미 소진된 일일 한도는 즉시
복구할 수 없으므로 해당 종목은 오류를 표시하고 24시간 뒤 다시 조회합니다.

## 14. 목표 비중 합계와 자산 범위가 일치하지 않음

### 현상

목표 비중을 입력했지만 저장되지 않거나 통합 화면과 증권사 화면의 현재 비중이 다르게
보일 수 있습니다.

### 원인과 해결

- 목표 비중 합계가 정확히 100%가 아니면 저장하지 않습니다. 현금 행도 목표에 포함합니다.
- 통합/NH/키움은 서로 독립된 목표 세트이므로 `Tab`으로 선택한 범위를 확인합니다.
- 현재 비중은 해당 범위의 원화 평가금액과 원화 환산 현금을 합친 값을 기준으로 합니다.
- 미연결 증권사는 자산이 없으므로 현재 비중이 0%로 표시될 수 있지만 다른 증권사의
  자산과 목표에는 영향을 주지 않습니다.
- `r`은 현재 비중을 소수점 둘째 자리로 복사하므로 반올림으로 합계가 100%에서 조금
  벗어날 수 있었습니다. 현재는 반올림 후 가장 큰 비중 행에 잔여 오차를 반영해 합계를
  정확히 100.00%로 보정합니다.
- `a`로 추가한 미보유 종목이 잠시 보인 뒤 사라지는 원인은 5초 계좌 갱신 결과가 아직
  저장하지 않은 화면 상태를 SQLite의 기존 목표 목록으로 덮어썼기 때문입니다. 편집·추가
  후에는 dirty 상태를 유지해 자동 갱신과 늦게 도착한 비동기 응답을 무시합니다.
- 편집 중에는 `s`로 저장하거나 `u`로 되돌리기 전까지 통합/NH/키움 범위 전환을 막아
  다른 범위의 목표가 미저장 값을 덮어쓰지 않게 합니다.

## 검증 방법

- `httptest` 서버로 OAuth, 인증 헤더, 연속조회와 응답 변환 계약 검증
- 이동평균, 봉 집계, 급등 점수의 순수 도메인 단위 테스트
- SQLite 마이그레이션, 검색, 관심종목과 캔들 캐시 테스트
- mock 공급자를 이용한 애플리케이션 서비스 흐름 테스트
- TUI의 표·차트 렌더링과 키 입력 상태 전환 회귀 테스트
- NH 단독 다중 통화 잔고 집계, NH 환율 파생과 일시 실패 시 마지막 정상값 유지 테스트
- 일별 성과 합산, 기간 마지막 값 집계와 표/선 그래프 전환 테스트
- 증권사별 환율 격리와 실시간·혼합·캐시 상태 렌더링 테스트
- 배당 공급자 계약, 24시간 캐시, 세전·세후·원화 환산과 월별 예상 집계 테스트
- `go test ./...`, `go vet ./...` 전체 통과
- 프로세스와 SQLite 연결을 다시 만든 뒤에도 24시간 캐시가 재사용되고 공급자 호출 횟수가
  증가하지 않는 재실행 회귀 테스트
