# minstock 개발 포트폴리오

> 최종 갱신: 2026-09-29
> 상태: v0.2 조회 전용 MVP 개발 중
> 실행 명령: `minstock`

## 프로젝트 한 줄 소개

minstock은 NH투자증권과 키움증권의 국내·미국주식 계좌, 관심종목, 시세와
차트를 하나의 터미널에서 조회하는 Go 기반 TUI 애플리케이션이다. 금융 프로그램의
안전성을 위해 주문 기능을 구현하지 않고, 조회 API만 허용하는 명시적 안전 경계를
코드에 적용했다.

## 해결하려는 문제

- 여러 증권사와 국내·해외 계좌에 흩어진 자산을 한 화면에서 확인한다.
- 웹이나 모바일 앱을 오가지 않고 키보드만으로 검색, 관심종목과 차트를 탐색한다.
- 증권사마다 다른 응답 형식을 공통 도메인으로 변환한다.
- API 호출 제한과 네트워크 지연 속에서도 빠르고 안정적인 사용자 경험을 제공한다.
- 실제 금융 자격증명을 평문 파일이나 SQLite에 남기지 않는다.

## 담당 범위와 주요 결과

- Go 애플리케이션 구조, 증권사 어댑터, SQLite 저장소와 Bubble Tea TUI를 설계했다.
- 키움과 NH의 국내·미국주식 계좌 조회를 공통 포트로 통합했다.
- 한국/미국 보유종목 탭과 평가손익·수익률·보유비중 표를 구현했다.
- 종목 검색(국내·미국 마스터), 국내·미국 관심종목(키움 `ka01300/ka01301`,
  `usa20200/usa20201`) 동기화, 급등 후보 분석과 틱·분·일·주·월·년 차트를 구현했다.
- 티커·종목명·종목코드 중 일치하는 값을 SQLite에서 검색하고 결과 표에 티커를 표시한다.
- 키움 미국주식 종목 마스터(`usa10099`)는 명시적 동기화 시에만 가져오고, 계좌별
  1분 5회 호출 제한을 고려해 시작 시 자동 전체 동기화를 하지 않는다.
- 상세 화면 상단 전체 폭에 캔들 차트를 배치하고, 하단에 주식정보와 규칙 기반 분석을
  배치했다. MA5·MA20·MA60·MA120은 서로 다른 색의 선으로 표시하며 개별 토글한다.
- Vim 스타일 상태 기반 키 입력과 콜론 명령을 구현했다.
- OS Keychain 자격증명 저장, API rate limit, timeout과 OAuth 재인증을 적용했다.
- 주문 API ID와 경로를 허용 목록에서 제외하고 네트워크 요청 전에 차단했다.
- 최초 데이터 표시를 측정하고 캐시 우선·점진적 갱신 구조로 개선했다.
- 증권사·계좌·통화별 일별 자산 스냅샷과 일·주·월·연 포트폴리오 성과 선 그래프를
  구현했다.
- 키움/NH별 총자산·손익·수익률·미국자산·적용환율·자산비중을 독립 집계한다.
- 금액의 실시간·혼합·캐시 상태, 기준 시각과 환율 제공 증권사를 TUI에 표시한다.
- Alpha Vantage 배당 이력을 24시간 캐시해 종목별·월별 세전·세후 예상 배당을 계산한다.
- 목표 비중을 범위별로 로컬 저장하고 현재 평가액·현금과 비교해 편차와 집중도를 조회한다.

## 기술 스택

| 영역 | 기술 | 선택 이유 |
|---|---|---|
| 언어 | Go 1.27 | 단일 바이너리 배포, 명시적 인터페이스, 동시성 지원 |
| TUI | Bubble Tea v2 | Elm 방식의 Model–Update–View 상태 관리 |
| 스타일 | Lip Gloss v2 | ANSI 색상, 테두리, 너비와 정렬 처리 |
| 차트 | ntcharts v2 | 터미널 캔버스 기반 시계열 그래프 |
| DB | modernc.org/sqlite | CGO 없이 로컬 검색·캐시·마이그레이션 지원 |
| 금융 수치 | shopspring/decimal | 환율과 해외주식 소수점 계산의 정확성 |
| 설정 | go-toml v2 | 사람이 읽을 수 있는 플랫폼별 설정 파일 |
| 자격증명 | go-keyring | macOS Keychain/Linux Secret Service 연동 |
| 요청 제어 | x/time/rate | 증권사 호출 제한 준수 |
| 테스트 | Go testing, race detector, go vet | 기능·동시성·정적 오류 검증 |

## 아키텍처

```text
cmd/minstock
    │
    ├── config + OS keyring
    │
    └── Bubble Tea TUI
            │
       Application Service
            │
       Domain + Ports
         ┌──┴───────────────┐
         │                  │
  Broker Adapters      SQLite Repository
  ┌──────┴──────┐      ├─ 종목 검색 인덱스
  │             │      ├─ 관심종목
Kiwoom         NH      ├─ 캔들 캐시
REST/OAuth  REST/OAuth ├─ 대시보드 스냅샷
                       └─ 일별 자산 스냅샷
```

TUI는 증권사의 JSON 필드나 API ID를 알지 않는다. 애플리케이션 서비스는
`PortfolioReader`, `MarketDataProvider`, `WatchlistReader`, `FXProvider` 같은
작은 포트에 의존하고, 각 증권사 어댑터가 응답을 공통 도메인으로 변환한다.

## 주요 기술적 난관과 해결

### 1. 서로 다른 증권사 응답 통합

문제: 국내·미국 계좌마다 종목코드와 티커, 통화, 거래소, 평가금액 필드가 달랐고 같은
의미의 수치도 문자열과 부호 형식이 달랐다.

해결: 증권사 DTO를 어댑터 내부에 격리하고 `Balance`, `Position`, `Quote`,
`Candle` 공통 모델로 정규화했다. 미국주식에는 거래소 라우팅 코드와 USD 통화를
명시했으며 국내 티커는 종목코드로 보완하고 KRW와 USD를 환율 없이 직접 합산하지 않았다.

### 2. 조회 전용 안전 경계

문제: 실계좌 키를 사용하는 프로그램이므로 실수로 주문 API를 연결할 위험을
구조적으로 차단해야 했다.

해결: 조회 포트와 주문 개념을 분리하고 현재 실행 경로에는 주문 포트를 두지 않았다.
키움 클라이언트는 조회 API ID와 경로의 쌍을 allowlist로 관리하며 목록에 없는 호출은
HTTP 요청 전에 거부한다. 주문 경로 차단은 자동 테스트로 검증한다.

### 3. 자격증명 보안

문제: App Key와 Secret을 TOML이나 SQLite에 저장하면 저장소 유출 시 금융 계정이
위험해진다.

해결: 자격증명은 OS Keychain에 저장하고 입력할 때 터미널 echo를 끈다. 설정과
진단에는 준비 상태와 안전한 endpoint만 표시하며 키, Secret과 접근 토큰은 출력하지
않는다.

#### 키체인 저장 위치와 저장 검증 이슈

`minstock setup kiwoom`은 환경변수에 값을 쓰는 명령이 아니다. `go-keyring`의
macOS backend가 `/usr/bin/security add-generic-password`를 호출해 `minstock`
서비스와 `kiwoom.app_key`, `kiwoom.app_secret` 계정으로 기본 키체인에 저장한다.
일반적으로 이 저장소는 사용자의 로컬 로그인 키체인(`login.keychain-db`)이며,
iCloud Keychain에 자동 동기화된다고 가정하지 않는다. tmux는 셸 환경변수만 유지할
뿐 키체인 저장 위치나 수명을 바꾸지 않는다.

초기 구현에서는 저장 성공 메시지를 `keyring.Set`의 반환값만으로 판단했다. 이후
등록 다음 날 `--diagnose`에서 자격증명이 `미설정`으로 나타나 실제 저장 여부를
확인할 수 없었던 사례가 발생했다. 코드에는 삭제 경로가 없었고, macOS 기본 키체인
변경·초기화, 다른 키체인 컨텍스트, 환경변수와 키체인의 혼동 가능성을 분리해
점검했다. `security find-generic-password`로 항목 존재 여부를 값 노출 없이 확인했다.

해결책으로 `Security.Save()`가 두 값을 저장한 뒤 키체인 backend에서 즉시 다시
읽어 입력값과 일치하는지 검증하도록 보강했다. 검증 실패 시 성공 메시지를 출력하지
않으며, `--diagnose`는 `os-keyring`과 `environment` 출처를 구분해 표시한다. 이
경험을 통해 금융 자격증명은 저장 API의 성공 반환만 믿지 않고 저장 후 읽기 검증,
출처 진단, 키체인과 iCloud의 저장 경계 문서화를 함께 제공해야 한다는 점을 배웠다.

후속 장애 분석에서는 새 터미널에서만 연결이 실패하고 `security` 직접 조회는 성공하는
현상을 재현했다. `--diagnose`의 backend 오류가 `exit status 36`으로 나타났고, 이는
자격증명 삭제가 아니라 로그인 키체인(`login.keychain-db`)이 잠겨 사용자 상호작용이
허용되지 않은 경우였다. `security unlock-keychain`으로 잠금을 해제하자 새 터미널에서도
동일한 바이너리가 정상 연결됐다. 키체인 자동 잠금 시간을 늘리는 방법도 있지만,
잠자기 시 잠금을 해제하면 분실 시 위험이 커지므로 보안과 편의성의 균형을 문서화하고
필요할 때만 명시적으로 잠금 해제하는 운영 원칙을 선택했다.

### 4. 한글과 ANSI 색상이 포함된 표 정렬

문제: 한글은 터미널 표시 폭이 2칸이고 ANSI 색상 코드는 문자열 길이에 포함되므로
일반 `fmt` 폭 지정만으로 헤더와 데이터가 맞지 않았다.

해결: Lip Gloss의 표시 폭 계산을 사용해 잘라내기, 좌우 패딩과 정렬 함수를 만들었다.
좁은 터미널의 보유종목 표는 `[`/`]`로 열 구간을 이동하고, 선택 배경과 손익 전경색을
분리해 상승 빨강·하락 파랑을 유지한다.

### 5. Vim 스타일 입력과 검색 포커스 충돌

문제: `j`, `k`, `q`는 검색어가 될 수도 있고 전역 명령이 될 수도 있다.

해결: 검색 편집 모드, 일반 모드, 콜론 명령 모드와 `g` 대기 상태를 명시적으로
분리했다. 입력 모드에서는 문자를 검색어로 처리하고 방향키로 결과를 이동하며,
일반 모드에서는 `j`/`k`, `gg`/`G`, `gt`/`gT`를 탐색 명령으로 해석한다. `3`은
검색 일반 모드로만 진입하고 `/`가 입력 포커스를 활성화한다. 기본 화면 이동에는
번호키 외에도 `h`/`l`과 좌우 방향키를 제공한다.

### 6. 데모 데이터의 실사용 DB 잔존

문제: API 연결 전에 생성된 MOCK 관심종목이 실제 계좌 연결 뒤에도 SQLite에 남았다.

해결: 마이그레이션에서 `MOCK/sample` 그룹만 삭제하고 사용자가 직접 추가한
`MOCK/default` 로컬 관심종목은 보존했다. 이 동작을 마이그레이션 회귀 테스트로
고정했다.

### 7. 느린 최초 실행

문제: 시작 시 종목 전체 동기화와 계좌 조회를 동시에 수행하고, 모든 보유·관심종목의
현재가와 급등 분석이 끝난 후에야 첫 데이터를 표시했다. 5초 타이머가 느린 요청과
겹칠 가능성도 있었다.

측정 결과:

| 시나리오 | 변경 전 |
|---|---:|
| 전체 동기화와 대시보드 동시 실행 | 5.81초 |
| 대시보드만 실행 | 4.45초 |
| 전체 동기화만 실행 | 1.33초 |

해결:

1. SQLite의 마지막 대시보드 스냅샷을 먼저 표시한다.
2. 최신 잔고·보유종목·환율을 핵심 단계로 조회해 캐시 화면을 교체한다.
3. 종목별 현재가와 급등 분석은 별도 보강 단계에서 채운다.
4. 매 실행의 전체 종목 동기화를 제거하고 최초 캐시가 없을 때 또는 `:s`에서 수행한다.
5. 조회·보강·동기화 진행 상태를 추적해 5초 자동 갱신이 중복 실행되지 않게 한다.

변경 후 실계좌 재측정:

| 단계 | 소요 시간 |
|---|---:|
| SQLite 캐시 화면 준비 | 0.527ms |
| 최신 잔고·보유종목 핵심 조회 | 1.024초 |
| 현재가 14개와 급등 분석 보강 | 3.388초 |

첫 실행의 전체 최신화 시간은 비슷하지만, 재실행 체감 대기 시간은 약 5.81초에서
1ms 미만으로 줄었다. 약 1초 후 최신 계좌 데이터가 캐시를 교체하고 시세는 화면을
막지 않은 채 백그라운드에서 보강된다. 수치는 2026-08-27 실계좌 조회 1회 기준이며
네트워크와 증권사 API 상태에 따라 달라질 수 있다.

```text
SQLite cache ──즉시──> 화면
                          │
계좌·환율 API ───────────> 핵심 데이터로 교체
                          │
종목 시세·분석 ─────────> 점진적 보강
```

### 8. 일별 자산 기록과 기간별 성과 그래프

문제: 현재 잔고만으로는 어제 대비 자산 증감이나 장기 추이를 계산할 수 없다. 여러
증권사와 KRW/USD 계좌를 단일 숫자로 저장하면 어떤 환율로 환산했는지 잃고, 같은 날 앱을
여러 번 실행하면 중복 기록이 생길 수 있다.

해결: 계좌 조회가 끝날 때 증권사·해시 계좌 참조·통화를 복합 키로 삼아 하루 한 행의
`portfolio_snapshots`를 upsert한다. 현금, 매입금액, 평가금액과 손익은 원통화와 원화
환산값을 함께 저장하고 USD 행에는 당시 적용 환율을 남긴다. 원계좌번호, API 키와 토큰은
스냅샷에 저장하지 않는다.

성과 화면에서는 같은 날짜의 모든 행을 합산한 뒤 다음 값을 계산한다.

- 총자산: 원화 현금 + 원화 평가금액
- 평가손익: 증권사 원화 손익의 합
- 자산 증감: 현재 기록 총자산 - 직전 기록 총자산
- 증감률: 자산 증감 ÷ 직전 기록 총자산

일간은 모든 날짜를 사용하고 주간·월간·연간은 각 기간의 마지막 기록을 대표값으로
선택한다. `Tab`으로 표와 선 그래프를 바꾸고 `t`로 집계 주기를 순환한다. 선 구간과
표의 평가손익·증감·증감률은 상승 빨강, 하락 파랑, 변화 없음 흰색으로 통일했다.
입출금을 별도 현금흐름으로 분리하지 않았으므로 자산 증감률이 투자수익률과 다를 수
있다는 안내를 화면에 표시한다.

### 9. 증권사별 자산 현황의 독립 집계

문제: 통합 현황이 하나의 전역 USD/KRW에 의존하면 키움 인증 실패가 NH 원화 환산까지
막는다. 반대로 전체 합계만 표시하면 어떤 증권사의 자산과 환율이 반영됐는지 확인하기
어렵다.

해결: 공통 `Balance`를 증권사별로 먼저 집계하고 그 결과를 다시 전체 합계로 합친다.
USD 잔고는 해당 잔고의 증권사 환율을 우선 사용하며, 명시적 환율이 없을 때도 같은
증권사가 제공한 환율만 fallback으로 허용한다. 키움과 NH 행은 각각 총자산, 평가손익,
총 매입금액 기준 수익률, 미국자산, 적용환율과 전체 자산 비중을 계산한다. 연결 상태는
있지만 잔고가 없는 증권사는 `데이터 없음`으로 남겨 다른 증권사의 계산을 중단하지 않는다.

### 10. 데이터 신선도와 환율 출처 전파

문제: SQLite 시작 캐시와 NH 어댑터의 5초 공유 캐시, 장애 시 마지막 정상 잔고가 모두
같은 `Balance`로 반환돼 TUI가 실시간 응답과 구분할 수 없었다. 데이터 유실을 막기 위한
fallback이 오히려 오래된 값을 최신값처럼 보이게 만들 수 있었다.

해결: 도메인 잔고와 포지션에 `Freshness`와 `AsOf`를 추가했다. 키움과 정상 NH 응답은
`LIVE`, NH의 공유·장애 fallback은 `CACHED`, SQLite에서 복원한 전체 스냅샷은 `CACHED`로
표시한다. 한 증권사 안에 live와 cached 행이 함께 있으면 `MIXED`로 합성하며 기준 시각은
포함된 데이터 중 가장 오래된 시각을 사용해 과도하게 최신으로 보이지 않게 한다.

80열 화면은 `●실시간`, `◐혼합`, `○캐시`의 짧은 범례를 사용한다. 넓은 화면에서는
증권사별 상태와 `HH:MM:SS` 기준 시각을 표시하고, 환율에는 `[NH·실시간]` 또는
`[키움·캐시]`처럼 제공자와 상태를 함께 붙인다. ANSI 색상을 적용하기 전에 셀 너비를
맞추는 방식을 유지해 방향 색상과 상태 문구가 추가돼도 표 정렬이 깨지지 않게 했다.

### 11. API 호출 예산을 고려한 배당 예상 조회

배당 데이터는 증권사 잔고 API에 포함되지 않아 별도 소스가 필요했다. 미국 ETF를
지원하고 과거 배당과 이미 선언된 미래 배당을 함께 반환하는 Alpha Vantage의
`DIVIDENDS` endpoint를 선택했다. API 키는 `minstock setup dividend`로 OS 키링에
저장하며 설정·SQLite·로그에는 남기지 않는다.

무료 키의 일일 호출 예산을 보호하기 위해 심볼별 응답을 24시간 캐시한다. 배당이 없는
종목의 빈 응답도 캐시해 같은 심볼을 반복 호출하지 않는다. API가 실패하면 저장된 응답을
사용하고 화면에 캐시 상태를 표시한다.

계좌는 5초마다 갱신되지만 보유종목·수량·환율의 조합이 동일하면 배당 보고서를 다시
요청하지 않는다. 상태가 바뀌어 재계산하더라도 유효한 24시간 종목 캐시를 먼저 사용한다.
화면 진입과 계좌 갱신이 겹칠 때 같은 심볼 요청이 중복되지 않도록 진행 중 요청을
single-flight 방식으로 합친다. 캐시가 없는 종목의 일반 실패는 15분, Alpha Vantage
일일 한도 오류는 24시간 negative cache로 보관해 5초 자동 갱신이 API 호출 폭주로
이어지지 않게 했다. 실패한 종목은 경고로 분리하고 성공한 종목의 보고서는 유지한다.

연간 예상 배당은 최근 12개월 주당 지급액 합계에 현재 보유수량을 곱한다. 같은 ETF를
여러 증권사에 보유하면 USD 금액은 합산하지만 원화 환산은 포지션별 증권사 환율을 각각
적용한다. 세후 금액은 미국 원천징수 15% 가정이며 개인별 조세 상황을 반영한 세무 계산이
아님을 화면에 명시한다. 월별 캘린더는 선언된 미래 지급을 우선하고 아직 선언되지 않은
기간은 직전 지급일을 1년 뒤로 옮긴 추정치로 표시한다.

### 12. 주문과 분리한 목표 비중 분석

목표 비중은 `allocation_targets`에 통합·NH·키움 범위별로 저장한다. 현재 비중은 원화
평가금액과 원화 환산 현금을 합친 총자산을 분모로 계산한다. 목표 합계가 100%가 아니거나
개별 비중이 0~100%를 벗어나면 저장하지 않는다. 편차는 현재 비중에서 목표 비중을 뺀
값이며 ±2% 이내를 적정, +5% 초과를 집중으로 구분한다. 이 화면은 조회 전용으로 유지해
주문 API와 매수·매도 수량 제안으로 연결하지 않는다.
현재 미보유 종목도 로컬 종목 마스터를 검색해 0% 현재 비중의 목표 자산으로 추가할 수 있다.
잔고 총자산과 개별 포지션·현금의 합이 일치하지 않으면 차액을 `기타 자산`으로 표시해
대시보드와 리밸런싱 화면의 총자산 분모가 달라지지 않게 한다.

현재 비중 복사는 각 행을 소수점 둘째 자리로 반올림한 뒤 가장 큰 비중 행에 잔여 오차를
더해 목표 합계를 정확히 100%로 맞춘다. 목표값 편집과 미보유 종목 추가는 dirty 상태로
관리하며, dirty 상태에서는 계좌 자동 갱신 응답과 이전 비동기 응답이 화면의 미저장 값을
덮어쓰지 못한다. 범위 전환은 저장 후 허용하고 `u`로 SQLite의 마지막 저장 상태를 다시
불러올 수 있다.

## 데이터 저장 원칙

- Key와 Secret: OS Keychain
- 설정과 endpoint: TOML
- 티커·종목명·코드·시장: SQLite 검색 인덱스
- 사용자가 열어 본 확정 캔들: SQLite 캐시
- 마지막 화면 스냅샷: SQLite JSON 캐시
- 일별 자산 스냅샷: 증권사·해시 계좌 참조·통화별 원통화/원화 금액과 적용 환율
- 키움 접근 토큰: 프로세스 메모리
- NH 접근 토큰과 만료 시각: OS Keychain (24시간 내 재실행 시 재사용)
- 주문 데이터: 저장하지 않음—주문 기능 자체가 없음

대시보드 캐시에는 화면에 표시됐던 금융 데이터가 포함되지만 자격증명과 토큰은 없다.
데이터 디렉터리는 사용자 전용 권한으로 생성한다.

## NH PLUG 명세 변경 대응

NH 연결은 성공했지만 총자산만 합산되고 보유종목이 보이지 않는 문제가 있었다. 캐시를
증권사별로 집계해 보니 NH 평가금액은 수신됐지만 NH 포지션 배열은 비어 있었다. 2026년
9월 KRX 거래시간 관련 명세 변경으로 국내 잔고 요청에 `aly_qut_cd`가 필수가 된 사실을
공식 SDK와 최신 OpenAPI 명세에서 확인해 정규장 기준값을 추가했다.

또한 평가금액과 보유종목을 만들 때 동일한 국내 잔고 API를 두 번 호출하던 구조가 호출
한도 오류를 유발했다. 계좌별 잔고 응답을 짧게 재사용하여 한 번의 응답에서 Balance와
Position을 모두 변환하도록 개선했다. NH 해외주식은 별도 `gbstock` 잔고 API를 호출해
USD 포지션으로 합치며, 국내주식과 미국주식 탭에서 각각 같은 NH 계좌의 종목을 볼 수
있다.

NH는 접근 토큰을 새로 발급할 때마다 사용자에게 보안 알림을 전송한다. 기존 구현은
프로세스 안에서만 토큰을 캐시해 앱을 다시 실행할 때마다 유효한 토큰이 있어도 새로
발급했다. 토큰과 만료 시각을 OS Keychain에 저장하고 만료 1분 전까지 재사용하며,
서버가 401을 반환할 때만 캐시를 지우고 한 번 재발급하도록 바꿨다.

## 실서비스 연결 트러블슈팅

### 키움 토큰 오류 `8050`

App Key와 Secret을 정상적으로 읽었는데도 토큰 발급이 거절됐다. 응답 본문을 확인하니
키 오류가 아니라 `IP가 등록되지 않았습니다`였다. 키움 REST API는 App Key 관리 화면에
등록된 공인 IP에서만 인증을 허용한다. 본가에서는 연결되지만 다른 가정에서는 실패했던
사례를 통해 실행 장소와 VPN에 따라 공인 IP가 달라지는 점을 확인했다. 연결 진단에서
자격증명 유무와 서버가 반환한 인증 사유를 구분해 해석해야 한다.

### 나무PLUG QR 오류 `91800`

API 신청 QR을 모바일에서 열었을 때 요청 정보가 없거나 시간이 초과됐다는 오류가
발생했다. QR은 PC 브라우저가 만든 짧은 수명의 인증 요청이므로 오래된 화면을 재사용하지
않고 PC 페이지를 새로고침한 직후 나무증권 앱으로 스캔해야 했다. 이 단계는 API 키 발급
전 포털 인증이므로 minstock의 OAuth 구현과는 독립적인 문제였다.

### NH live 모드와 mock endpoint 불일치

설정에서 `mode = "live"`만 변경하고 `base_url`이 `moapi.nhplug.com`으로 남아 TUI에는
NH `mock connected`가 표시됐다. 실제 호출 대상은 mode 문자열이 아니라 endpoint로
결정된다. 운영 연결에서는 mode, base URL과 auth URL을 함께 점검하고 `--diagnose`에
표시된 endpoint를 기준으로 확인한다.

### NH 호출 제한 `IGW42903`

평가금액과 종목 목록을 만들기 위해 같은 국내 잔고 endpoint를 연속 두 번 호출하면서
APP+API 호출 한도를 초과했다. 계좌별 잔고 응답을 짧게 캐시해 Balance와 Position이
공유하게 했으며 HTTP 429에서는 토큰을 폐기하거나 재발급하지 않는다. 자동 갱신도 이전
조회가 끝나기 전에 겹치지 않도록 상태로 제어한다.

### 연결됐지만 NH 종목이 보이지 않음

SQLite 대시보드 캐시를 증권사별로 집계해 NH 총평가금액은 존재하지만 NH Position은
0개라는 사실을 확인했다. 국내 잔고에는 최신 필수 파라미터를 추가했고, 별도 해외주식
잔고 endpoint의 `Output_1`을 USD Position으로 변환했다. 연결 상태, 계좌 합계와 종목
배열을 단계별로 나눠 검사한 것이 원인을 좁히는 데 효과적이었다.

### NH 토큰 발급 알림 반복

NH는 접근 토큰을 발급할 때마다 사용자에게 보안 알림을 보낸다. 프로세스 메모리만
사용하던 구현에서는 앱 재시작마다 알림이 발생했다. 유효기간이 남은 토큰을 OS
Keychain에 보관하고 재사용하도록 변경했으며 만료 임박 또는 HTTP 401에서만 재발급한다.
토큰은 App Key의 짧은 해시와 함께 저장해 다른 키의 토큰을 재사용하지 않으며, 진단
출력과 SQLite 대시보드 캐시에는 포함하지 않는다.

  더 중요하다.
- API 응답을 모두 모아 하나의 거대한 스냅샷으로 반환하면 단순하지만 느린 한 요청이
  전체 UI를 막는다. 핵심 데이터와 보강 데이터를 나누는 편이 사용자 경험과 장애
  격리에 유리하다.
- TUI도 웹 UI처럼 포커스, 비동기 요청, 오래된 응답과 반응형 레이아웃을 명시적으로
  설계해야 한다.
- 금융 프로그램은 기능 구현보다 권한 경계, 통화 정확성, 비밀값 관리와 실패 시
  동작을 먼저 설계해야 한다.

## 다음 개선 과제

- 종목별 시세 보강의 제한된 병렬 처리와 provider별 호출 예산 관리
- 목표가·변동률·손실률·비중·연결 실패의 로컬 TUI 알림 이력
- 종목 마스터 동기화 TTL을 `broker_sync_state`에 기록
- WebSocket 기반 관심종목 실시간 시세
- 테스트용 지연·실패 주입 provider와 시작 성능 회귀 벤치마크

기능별 순서와 완료 기준은 [FEATURE_ROADMAP.md](FEATURE_ROADMAP.md)에서 관리한다.

## 문서 유지 규칙

이 문서는 프로젝트 포트폴리오의 기준 문서다. 다음 변경이 생기면 코드와 같은 작업에서
함께 갱신한다.

- 프레임워크, 라이브러리 또는 외부 API 추가·교체
- 아키텍처와 데이터 흐름 변경
- 사용자에게 보이는 주요 기능 추가
- 성능·보안·정확성 문제와 해결 방법
- 측정 가능한 개선 결과와 새 테스트 전략

일상적인 문구 수정이나 작은 스타일 변경은 누적하지 않고, 기술적 판단과 문제 해결
과정을 설명할 가치가 있을 때 기록한다.
